# 全局15GB存储候选

本分支是独立开发候选，基于生产 `9e2d1ee`，保留其18项主线外修复，再整合现有
备份池、任务备份复用和Kopia回环三提交。没有启用生产、挂载磁盘、清理旧数据或
上传真实数据。正式配置、数据库Schema、Master、原图和唯一恢复材料不变。

## 容量契约

- 硬上限为 `15_000_000_000` 字节，约13.97 GiB；所有登记的Action本地文件及
  临时峰值合计计算。不能把备份、导出、模型缓存或另一F盘目录排除在外。
- 全局范围由明确roots和目录发现锚点共同定义。新出现的Action旧式目录也纳入；
  单靠文件名不能证明全盘没有未登记副本，生产启用前仍须完成目录收口和引用核验。
- 盘点不忽略未知文件、WAL/SHM、临时文件、日志或控制记录；重叠目录及相同inode
  的硬链接只计一次。逻辑长度与实际分配量取较大者；不依赖压缩节省的估算。
- 重解析点、不可读路径、未知文件类型、坏账本、变化的scope/limit均阻断，不把
  无法测量的资产当成0字节。
- 超额只返回BLOCKED，不自动删除、缩减范围、放大限制或改到其他盘/目录继续写。

## 硬限制与预留

`operations.global_capacity`复用Storage Foundation的OS锁、文件分配量测量和
封存Hash。单一持久账本记录任务、目标、基准占用、最坏新增峰值、PID及所有权。

写入条件：实际总量 + 其他未物化预留 + 本次最坏峰值 + 控制开销 <= 上限。
并发不同目标的任务共同预留；重叠写入目标不能另开额度。落盘增长消耗已有预留，
避免把已物化字节又当未来空间重复收取。失败保留载荷和预留，不按TTL回收；同一
任务明确Resume时验证绑定和进程归属，不重复创建数据库基线。

任务开始时完整盘点；运行期间使用受限卷实际已用空间（含文件系统和未登记文件）
进行快速检查。单任务按卷的真实增长消耗预留，多任务仍分别核算各自目标，避免
每个字段重复全目录扫描。实际受限卷比15GB更小时，以其可用容量进一步收紧。

程序预算不能限制绕过API的第三方库写入。故**写入准入还必须验证所有scope实际
位于同一受限文件系统，操作系统报告的总容量不大于限额**。普通大容量F盘即使
只有几KB数据也拒绝启用。当前没有自动创建或迁移VHDX；若将来使用虚拟磁盘，
宿主容器及封装开销也须独立纳入整体15GB验收，不能重复计数或藏在scope外。
该底层门禁防止把Python估算/事后报警包装成已实现的操作系统配额。

当前真实历史范围明显超过15GB，因此候选配置的正确行为是BLOCKED。先保留
原件并明确资产退出方案，再另行授权迁移和启用；本分支不为达标擅删历史数据。

## 接入与兼容

- CLI在创建runtime目录和日志之前进入全局容量上下文。
- `--storage-policy PATH`或`ACTION_TRACKER_STORAGE_POLICY`覆盖早期backup-pool/
  pool-kopia/storage-foundation入口；普通生产配置可通过`global_storage`接入。
- CLI容量上下文约束TEMP/TMP/TMPDIR和Python tempfile路径，离开后恢复旧环境。
  单进程使用锁防止并发篡改环境；库级任务上下文不修改进程全局环境。
- 原有database.connection、备份池和Verified Backup在目标检查/复制前检查额度。
  第三方写入的最终物理边界仍由受限文件系统提供。
- 启用全局模式后，daily临时工作区必须启用；默认使用控制根下的tasks。
  Resume复用原绑定目录。PRIMARY、Master、State、Snapshot、审批记录仍保留各自
  权威职责，不因“统一临时目录”被挪进可丢弃缓存。
- 备份仍通过原Storage Foundation/TaskBackupManager，完整任务共用一份独立恢复
  验证基线，批次留行级变化凭证。外部Head/Schema/文件身份变化拒绝复用。
- 原5GiB池策略保持旧调用兼容；启用全局模式后可显式配置不超过全局限额的池子
  子预算。改变既有池marker仍阻断，不自动收编或改写老池。
- 默认全局功能禁用，生产配置与部署Hash不被此分支自动更新。示例配置明确启用，
  但对当前真实F盘应阻断；没有“不验证底层限制”的生产开关。

只读盘点（不会初始化池/运行目录；旧数据超额返回2）：

```powershell
python -m action_tracker --storage-policy config/storage_global_15gb.example.yaml storage-capacity
```

常规业务命令可通过已有profile使用global_storage；原数据QA、审批、Immutable
Patch、ProductionWriter与export_sync全保留。显式storage-policy和运行配置的
project_root/scope不一致时拒绝，不隐式改变业务库位置。

## 回归与验收边界

CI_SAFE仅使用生成SQLite及隔离目录。覆盖合计超额、未知文件、WAL、硬链接、
并发预留、超额前拒写、受限卷缺失、坏账本、失败/Resume、环境恢复、原始池入口
不可绕过及20批同基线复用。小容量测试通过显式mock系统卷探针完成；没有拿
模拟卷测试冒充真实VHDX、生产迁移或15GB全量数据收口验收。

生产启用前另需：真实受限卷与封装开销证明、无scope外Action数据、副本/恢复义务
核验、SQLite/导出/Resume兼容演练和独立用户授权。任何一项不足均保持BLOCKED。
